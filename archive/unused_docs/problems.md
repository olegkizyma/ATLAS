Ниже структуровано всі помітні проблеми / ризики з логу.

1. Режим запуску (Flask)  
- Попередження: використовується dev-сервер Flask (WARNING: This is a development server...).  
- Ризик: небезпечно для продакшену (гаряче перезавантаження, однопотоковість, відсутність захистів).  
- Рішення: перейти на gunicorn / uvicorn (через WSGI/ASGI шар) + reverse proxy (nginx).

2. Надмірна кількість повторних WARNING inference_feedback_manager.cc  
- Повторюваний меседж: “Feedback manager requires a model with a single signature inference. Disabling support for feedback tensors.”  
- Ймовірна причина: завантажено TFLite-модель з декількома signature або некоректна конфігурація delegate.  
- Наслідок: відключено збір зворотних (feedback) тензорів → менш точні адаптивні механізми (якщо планувались).  
- Дії:  
  a) Перевірити tflite-модель (tflite_model.get_signature_list()).  
  b) Якщо потрібно feedback API — перегенерувати модель з одним основним signature.  
  c) Або вимкнути логування цих повторів (рівень / фільтр) щоб не засмічувати лог.

3. Повторні GL context логи (GL version …)  
- Симптом: багаторазова ініціалізація контексту.  
- Ризик: можлива повторна (непотрібна) ініціалізація рендеру / delegate, вплив на стартовий час.  
- Дії: перевірити чи не створюється інтерпретатор/процес кілька разів (debug reload Flask це робить). У продакшені зникне.

4. Flask debug / auto-reloader  
- “* Restarting with stat”, “Debugger is active!”  
- Це очікувано в dev, але спричиняє подвійну ініціалізацію ресурсів (модель, GL, delegate).  
- Рішення: вимкнути debug у продакшені (FLASK_ENV=production, debug=False).

5. Deprecation / FutureWarnings (Python stack)  
- pkg_resources deprecated (Setuptools < 81 pin або переписати імпорт; але тут всередині pyworld — можна лише стежити за оновленням пакету, зафіксувати версію в requirements).  
- Torch TypedStorage deprecated → майбутня версія PyTorch видалить. Перевірити власний код (чи є прямі виклики .storage()) — якщо ні, просто оновити при переході версій і відстежити changelog.  
- torch.nn.utils.weight_norm deprecated → замінити на torch.nn.utils.parametrizations.weight_norm у власному коді (якщо використовуєте напряму; якщо лише у залежності – дочекатися оновлення).  
- Рекомендовано: додати фільтри або централізований збір DeprecationWarnings, план міграції (дедлайн pkg_resources ~ листопад 2025).

6. Продуктивність (TTS на CPU)  
- Лог: “Resolved device selection: requested=cpu”  
- Якщо очікується GPU прискорення – додати авто-виявлення CUDA/MPS/Metal. На M1 можливе використання torch.backends.mps (якщо модель сумісна).  
- Інакше позначити свідоме рішення (конфіг-прапорець), щоб не сприймати як приховану деградацію.

7. Надмірна деталізація архітектури TTS (архітектурний дамп моделі)  
- Великий блок опису моделі у runtime логу засмічує потік.  
- Краще: логувати один рядок (тип, розмір параметрів) і в окремий debug-лог при потребі.  
- Дії: обгорнути print структури умовою (if verbose/debug flag).

8. Завантаження Stanza ресурсів кожен старт (або перевірка існування)  
- В логах видно послідовність завантаження; частину файлів уже є.  
- Оптимізація: кеш-контроль (перевіряти хеш / час) і приглушити INFO при кеш-хіті.

9. Відсутність агрегації health-check шуму  
- Запити GET /api/health, /api/vision/status, /health логуються повністю.  
- Якщо health-check частий (оркестратор / LB) — винести в DEBUG або окремий logger channel, щоб не «топити» корисні події.

10. Потенційне дублювання порт логів  
- Лог фронтенду показує і 0.0.0.0, і локальні IP — нормально, але можна скоротити до одного повідомлення для чистоти.

11. Відсутність явного маркування версій компонентів у старті  
- Є модельні попередження, але немає консолідованого “Startup summary” (версії Python, Torch, TFLite delegate, конфіг).  
- Рекомендація: один блок “STARTUP SUMMARY” після ініціалізації → полегшує діагностику без гори дрібних INFO.

12. Можливе зростання розміру логів  
- Через повторювані Warning (feedback manager) і структурний дамп — ризик швидкого росту файлу.  
- Дії: ротація (logging.handlers.RotatingFileHandler), або рівень WARN вище для повторів (rate limiting).

Класифікація за пріоритетом  
High: (1) Перехід з dev Flask для прод (безпека/стабільність), (2) Потік повторних inference_feedback_manager Warning (шум + можлива втрата функціоналу), (12) Ротація логів.  
Medium: (5) Deprecation warnings (підготовка до майбутніх релізів), (4) Подвійна ініціалізація через debug, (7) Надмірний дамп моделі.  
Low: (6) CPU замість GPU/MPS (якщо прийнятно), (8) Вербосність Stanza, (9) Health-check шум, (10) Подвійні адреси, (11) Відсутність summary-блоку, (3) Повтор GL (зникне в проді).

Конкретні наступні кроки (мінімальний план)  
1. Додати production entrypoint: gunicorn "app.atlas_server:app" -w 4 -b 0.0.0.0:5001 (або uvicorn якщо ASGI).  
2. Перевірити TFLite модель: підтвердити кількість signatures; за потреби конвертувати з одним signature.  
3. Ввести rate-limiter для повторних однакових warning (наприклад, cache ключів і подавлення після n).  
4. Прибрати детальний друк структури TTS або за прапорцем DEBUG.  
5. Додати rotating file handler (наприклад, maxBytes=10MB, backupCount=5).  
6. Зібрати список DeprecationWarnings у окремий розділ документа (міграційний чекліст).  
7. Опціонально: спробувати torch.mps для TTS (перевірка lat/rtf).  
8. Знизити рівень логування для health-check до DEBUG.  
9. Додати стартовий “SUMMARY” блок (версії, порти, режими).

Метрика успіху  
- Лог старту стискається до < 20 рядків ключової інформації.  
- Повторні inference_feedback_manager warning ≤ 1.  
- Відсутні DeprecationWarnings (або ізольовані в окремий лог).  
- Розмір лог-файлу після 1 години роботи без активних користувачів ≤ 1MB.

Якщо потрібна допомога у внесенні змін у код логування або створенні продакшен конфіг — скажи.
